# 古い当たり反応の再生前破棄：制約と設計案

Issue #152 / PR #155。調査基準は `ae064d2`。本変更では生成経路を増やさず、通常会話の実況抑制指示とゲーム文脈のACK待ち解除だけを実装する。以下の音声分離・3秒での再生前破棄は設計案であり、未実装。

## 現在の経路と限界

- `GameViewModel.revealSpin()` は実際のリール停止後に `spin_revealed(side, round)` を送る。サーバーは保存済みの確定した当たりと照合する。
- `MatchSession.sendRequiredWinReaction()` は現在も通常会話を強制中断し、GPT-Liveへ指示と当たり反応を送る。この強制中断は本変更では外していない。
- `GptLiveBridge` は当たり反応と通常会話を同じ `session.output_audio.delta` で受け取る。既存の `speechId` はアプリによる推定タグであり、元イベントとの対応をプロバイダーが保証するものではない。
- `LiveAudioPlayer` は受信PCMを順序どおりに再生する。通常の結果更新で古い反応だけを破棄する処理はなく、再生待ち時間に固定上限はない。

公式[GPT-Liveの文脈更新仕様](https://developers.openai.com/api/docs/guides/live-conversations#understand-when-context-reaches-the-model)では、appendのACKは文脈注入の進行に関する通知であり、発話・再生の完了や更新全体の消費を保証しない。フレーム進行が止まるとACKが保留され得る。

公式[WebSocketの音声仕様](https://developers.openai.com/api/docs/guides/voice-websockets?api=live#send-and-receive-events)では、出力音声イベントにタイミングフィールドもoutput-audio-doneもない。従って、実況送信の前後・`instructions.appended`・既存の200ms無音検出／4秒フォールバックを、通常会話と実況の確実な境界にはできない。字幕の時刻もPCMの正確な再生位置にはならない。

送信時にIDや期限を追加するだけでは、同じストリームから古い当たり音声だけを識別して取り除くことはできない。

## 本変更で実装する内容

1. 基本指示と通常時のゲーム文脈に、状態通知だけで当たりを実況しないことを追加する。ユーザーの当たりに関する質問には回答でき、明示された当たり反応要求にも従う。これはモデルへの指示であり、通常会話中の言及を完全に遮断するフィルターではない。
2. 文脈appendの5秒ACKタイムアウト時に、そのIDが現在の `contextInFlight` である場合だけ待ちを解除する。更新があれば最新の1件を送る。同じ内容の再試行は1回までに制限し、古い当たりの列を再送しない。後から来た旧ACKは新しい送信待ちを解除しない。新しい状態更新には新しい再試行枠を与える。

期限切れは文脈が拒否された証拠ではないため、再送が重複受理される可能性は残る。再試行するのは発話要求ではない状態通知のみ。実況・貸借・延長の台詞はこのタイムアウトで再送しない。

## 期限を分ける

| 制限 | 起点・判定 | 現状 |
| --- | --- | --- |
| 既存の送信前2秒 | 古い確定イベントの受付、およびサーバーの表示通知受信後から発話要求送信まで。両者当たりの表示待ちも最初の通知から2秒 | 実装済み。音声再生時刻の上限ではない |
| 提案する再生前3秒 | ブラウザが実際に当たりを表示した単調時計の時刻から、反応クリップを再生し始める直前まで | 未実装 |
| 同じ側の次の結果表示 | `side` ごとの表示済み `round` が対象を追い越したら、3秒以内でも失効 | 未実装 |

サーバーが次の結果を抽選した時刻とブラウザが表示した時刻は異なる。最終判定にはブラウザ自身の表示履歴を用い、サーバー／ブラウザの壁時計を単純比較しない。双方同時の反応は両方の対象を保持し、どちらかが古くなった時点で全体を失効させる。時刻・表示履歴が欠ける反応は再生しない。

## 必要な生成経路の分離案

通常会話は現在のGPT-Liveで継続し、明示的な当たり反応だけを「1要求につき1本の完結した音声」を返す独立した生成経路に分ける。

候補は[Audio Chat Completions](https://developers.openai.com/api/docs/guides/audio-chat-completions)による短い音声の一括生成。HTTPリクエストと完結した音声レスポンスをアプリ内で対応付けられるため、会話PCMを推測で切り分ける必要がない。既存の自然な反応指示と確定当たり情報だけを渡し、実際の会話やマイク音声は渡さない。追加API利用・モデル利用可否・声の一致・3秒以内の生成率は別途検証が必要。これは採用・実装済みのAPIではない。

将来実装する場合の流れ:

1. 実リール停止通知を保存済みの `side/round` と照合する。ブラウザにはその表示時刻を保存する。明示反応に固有IDと対象の組を割り当て、1回だけ独立した音声生成を依頼する。
2. 完全な生成成功と音声全体の受信を確認してから、ID付きのクリップとして届ける。途中失敗・打切り・期限切れはクリップ全体を破棄する。部分的なPCMを会話の再生キューに入れない。
3. ブラウザでは通常会話の再生中は反応を始めず、未再生の最新候補だけを保持する。次の結果表示・期限・終了で破棄し、再送や会話終了後の一括消化は行わない。
4. 実際に再生開始する直前に、3秒未満・対象の表示が現在も最新・試合中であることを再確認する。先の時刻に音声を予約するだけでは十分でなく、デコード待ちや停止タブからの復帰も含めて確認する。
5. 失効済みIDの後着音声・重複音声も拒否する。試合ごとの世代と照合し、再戦や再接続で旧音声を受け入れない。再生開始済みのクリップは期限や次の回転を理由に切らない。

LiveAvatar経由の映像・音声を同様に制御するには、実際の再生開始前にクリップ単位で取り消せるインターフェースが必要。現行実装では保証できない。別案は反応クリップのみブラウザで再生する方法だが、その反応の口パクは連動しなくなるため、採用判断が必要。

通常会話の音声には確実な終了境界がないため、無音だけを会話完了と決めない。反応の開始後に会話音声が到着した場合も、会話音声を一律破棄してはならない。発話を切らない条件に加えて完全な重なり防止まで求める場合は、会話とクリップの再生順序を管理する追加設計が必要。

## 検証の境界

本変更の自動検証は、状態通知と明示要求の指示の区別、ACK欠落後の最新状態の送信、旧ACKの無視、同一文脈の再試行上限、接続終了時のタイマー解放を対象とする。実音声の自然さ、遅延、プロンプトによる自発実況の抑制率は未検証。強制中断と未再生の古い反応を破棄する新方式の受け入れは、本変更で完了とはしない。

- `npm test`: 31ファイル / 632テスト成功。
- `npm run typecheck`、`npm run lint`、`npm run check:server-runtime`、`npm run build`: 成功。
- 外部音声APIの実呼出し・マイク収録・実会話による試験は実施していない。レビューは今回の対象外。
